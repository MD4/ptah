# PTAH V2 — AI (Step 6): the whole step, and piece 1 in detail

Date: 2026-11-23. Status: **approved by the owner on 2026-11-23.**

Base: master plan §4.6 and §4.3 (`2026-10-25-v2-master-plan.md`). This document replaces §4.6's order and adds what the owner decided on 2026-11-23. Code: `~/projects/ptah-v2`.

## Intent

The owner is the band's drummer. He lights his songs by instinct and wants PTAH to light new songs well, in his own style, following the good practices of stage lighting. He also opens PTAH to a few friends who do not use a terminal.

The AI is a lighting designer that proposes; the owner reacts by talking to it. It never plays a part in a running show.

## Decided with the owner (2026-11-23)

1. **Three features, in this order:** programs from a sentence; the show from the audio; the repatch assistant last (no gig on a foreign rig is booked).
2. **A conversation, not one shot.** The owner keeps talking to adjust a program ("slower", "more red") and the whole show ("the chorus of song 3 is too busy").
3. **The AI may create programs.** Each is marked *proposed* until the owner keeps it.
4. **The show from the audio** (piece 3 below):
   - Input: the folder of the rendered Reaper project, read by PTAH itself (the project file: tempo, regions, tracks; the rendered audio), plus the lyrics from a text or Markdown file.
   - The lights follow mainly the music; the lyrics only shade the mood.
   - One Reaper project holds the whole set, so the AI paces the whole night.
   - Per song the owner chooses "leave alone" (the default for a song he lit by hand) or "propose a redo".
   - An option "learn from my songs": his hand-lit songs are given as examples so the night stays consistent.
   - The result reaches Reaper in one of two ways, by a setting: a MIDI file written in the project folder, or written into the Reaper project itself (with a backup first).
   - While rehearsing, PTAH plays the AI's draft itself in time with Reaper's clock; nothing is written until the owner decides.
5. **Good practices.** The AI follows the good practices of stage lighting.
6. **How it runs:** through Claude Code (the `claude` command, on the owner's subscription) when it is installed; otherwise a Claude API key. The owner does not pay for extra services: nothing in this step may require a paid service beyond those two.
7. **How it is built: a tool belt.** PTAH offers the AI a small set of safe actions as an MCP server. PTAH checks each action and refuses a bad one with its reason. For songs, the AI writes a plan in plain words and PTAH turns it into exact MIDI. The AI never writes PTAH's files or MIDI by hand.
8. **The MCP server first, used from Claude Code; the panel inside PTAH second.**

## Goals, non-goals, anti-goals

**Goals.** A sentence gives a valid, editable program in seconds. Adjusting by talking works. Everything the AI makes is an ordinary PTAH file the owner can open, edit and keep without the AI.

**Non-goals.** Training or fine-tuning a model. Running a model on the machine. Any AI call from the Live screen. In piece 1: venues, patches, settings, Reaper, MIDI, a screen inside PTAH, the API-key path.

**Anti-goals** (it has failed if any of these happens, even if it works):
- The AI changes or deletes something the owner made, without him asking and seeing it.
- A show in progress is slowed, changed or broken by the AI.
- PTAH needs the AI, an account or the network to do what it does today.
- An invalid program or an off-beat note reaches a show.

## Approaches considered

1. **Free hand.** Claude Code works in a scratch copy of the show folder and writes program files and MIDI itself; PTAH checks and takes them. Least to build; but hand-written MIDI and JSON are where a model errs, and the key path would be a second, different build.
2. **A tool belt (chosen).** An MCP server with safe actions, each checked. Reliable; the same with Claude Code and with a key; each action is one step that can be undone; the plan for a song is readable. The most to build.
3. **One big answer.** One prompt, one complete result, checked and retried. Simple; but adjusting by talking redoes everything, and a whole set may not fit.

The owner chose 2.

## Piece 1: the tool belt, for programs

### What the owner does

Once: `claude mcp add ptah -- ptah mcp`. From then on Claude Code sees PTAH's tools.

Then, in Claude Code: "in HILLDALE, make a slow amber breathing program for the pars". In Effects the program appears:

```
Effects ▸ HILLDALE
  PARS PULSE          used by 3 rows
  WASH CHASE          used by 2 rows
  AMBER BREATHE       PROPOSED                 [ Keep ]  [ Discard ]
```

He keeps talking; the same program changes. If it is open in the Effects editor with no unsaved edit, the editor follows, and its Preview panel (the swatches on screen) shows each change. Keep makes it an ordinary program of the show. Discard deletes it (the usual danger confirm).

**On the real lights (owner, 2026-11-23: on screen first).** A proposed program is seen in the Preview panel. It reaches the real lights once it is kept and a row plays it, as with a program made by hand. Playing a proposed program on the rig on a temporary row is left to piece 3, which needs that ability for rehearsing drafts.

### How it is built (my calls unless marked)

- **`ptah mcp`** is a new subcommand: an MCP server over standard input and output, started by Claude Code. It is its own process. It links `ptah-model` (the node catalogue, the lint) and `ptah-vm` (to compute curves), and reaches the running PTAH through the local HTTP API (`127.0.0.1`, the settings' `uiPort`, or `--url`). The engine and the server's render path are not touched.
- **Every write goes through the API** (`PUT /shows/{id}/programs/{pid}` with `If-Match`, `DELETE`, `POST …/duplicate`), so the write lock, the validation and the issues are the Effects editor's own. The server gains what the proposed mark needs (below); the engine and the render path are not touched. If PTAH is not running, every tool answers "PTAH is not running. Start it, then try again."
- **MCP library or own code:** the server only needs tools over JSON-RPC on stdio. Write it by hand unless a crate, pinned exactly and older than 14 days, is clearly less code to own. No other new dependency.

### The tools

| Tool | Does | Refuses when |
|---|---|---|
| `practices` | Returns the rulebook and the owner's own rules | — |
| `status` | PTAH's version; the show playing; whether the clock runs | — |
| `list_shows` | Names and ids | — |
| `show` | A show's groups (with what their lights can do), rows (name, group, program), and programs (name, settings, used by, proposed or kept) | unknown show |
| `node_catalogue` | Every node kind: name, family, one sentence, its inputs, outputs and fields with their ranges | — |
| `program` | A program's full graph | unknown |
| `create_program` | Makes a *proposed* program from a name and a graph; returns its id, or the issues | invalid graph (issues returned); name taken; practices not read yet |
| `update_program` | Replaces a *proposed* program's name, graph and settings | not proposed; invalid; changed on disk since it was read (re-read first) |
| `copy_to_change` | Makes a proposed copy of a kept program, named "<name> (proposed)", remembering which it came from | unknown |
| `discard_program` | Deletes a *proposed* program | not proposed |
| `sample` | Computes a program over N bars at a tempo, with given setting values and a held or short note; returns, per output, a short series of values (and colour as words). It uses the same evaluator and the same made-up light with every capability as the Effects Preview panel (`ptah-web`'s `rig` and `session`); what a group's real lights can do is in `show`. | invalid program |

Rules across the tools:
- **Kept programs are never changed or deleted.** To change one, the AI makes a proposed copy; in Effects, Keep on such a copy offers "Replace <original>" (the copy's graph saved onto the original, through today's impact dialog) or "Keep as a new program".
- **Nothing a show uses is changed.** A proposed program is not part of its show yet (below), so no row can play it and changing it can never touch what plays. The tools write nothing else. (To the owner I said "no changes while the clock runs"; this is stronger and simpler.)
- **The rulebook is read first.** Write tools refuse until `practices` has been called in this session; the server's instructions say so.
- Tool results are short and plain; a refusal always says what to do next.
- **Going back.** Before `update_program` replaces a proposed program, `ptah mcp` writes the replaced file to `<root>/ai/history/<programId>/<n>.json` (n counts up from 1). `update_program` can take `revert: <n>`; `program` lists the numbers kept. The history of a program is deleted when it is kept or discarded. This is a new store: it is added to `docs/file-layout.md`. (`.backups` is for migrations only and is not used.)

### The *proposed* mark

A program file gains an optional `proposed` object: `{ "by": "ai", "from"?: "<programId>" }`, added to `program@1` without a version bump, as `notes` was (the Rust `Program` struct, `schemas/program.schema.json` and the TypeScript types all change).

**A proposed program is a file in the show's `programs/` folder that `show.json` does not list.** So making, changing or discarding one never writes `show.json`: the owner's unsaved edits on the Show screen are never put in conflict, and no row can play it. The server changes for this:
- `GET /programs` and the Effects list also return the unlisted files that carry `proposed` (marked so); an unlisted file without the mark stays ignored, as today.
- The program `PUT` accepts creating and replacing such a file without it being listed; the name rule (no two programs of a show with one name) counts proposed ones too.
- **Keep** is a new route: under the write lock it removes the mark and appends the program to the show's `programs` (a show `PUT`'s rules; if the show changed on disk, today's conflict answer). For a copy made by `copy_to_change`, Effects asks: "Replace <original>" (the copy's graph is saved onto the original through today's impact dialog, then the copy is deleted) or "Keep as a new program".
- The Show screen's "Add program" does not offer proposed programs.

Effects (the ZENITHALL screens, in `apps/web/src/builder` and `packages/ds/src/builder`; this piece is built after the redesign's last plan) shows the mark, Keep and Discard in the list, in the tiles (under `···`) and in the editor's bar. A proposed program opens, edits by hand, saves and previews on screen like any other; "On the rig" says it must be kept first.

### The rulebook

- A Markdown file bundled in the binary, returned by `practices`: for piece 1, the program-level rules (changes are smooth unless a hit is asked for; nothing flickers faster than a set rate unless strobe is asked for; colours that read on stage and on skin; a program exposes as settings what a show will want to drive: speed, colour, depth; it works for one light and for eight; names say what it does).
- The owner's own rules live in `<root>/ai/my-rules.md` (created empty with a comment on first use), returned after the bundled ones and winning over them.
- The rulebook's text is written during the build and read by the owner before the piece is called done.

### One source for the node sentences

Effects' add box has a sentence per node kind in TypeScript only (`packages/ds/src/builder/model/sentences.ts`); the Rust catalogue has a title, a family and search words. The catalogue the AI reads and the add box must show the same sentence from one source: move them or generate one side from the other, with a test that fails when they differ.

## Review and checks

- **Automatic:** a scripted MCP client drives `ptah mcp` against a real `ptah` (the e2e rig, `--fake-io`): each tool's good case and each refusal of the table; a created program loads in the Effects page marked proposed; a kept program's bytes and every `show.json` never change through any tool; `revert` gives back an earlier version; Keep lists the program in the show and removes the mark.
- **By the owner, with Claude Code:** five sentences of his choice, each adjusted twice; he judges whether the programs do what he said and reads the rulebook.

## Left to the builder

The exact shape of each tool's inputs and results; the JSON-RPC code; how `sample` reduces curves to a short series; how the editor notices a change on disk; where the node sentences live; the wording of refusals (short, plain, with the next step).

## Calls I made (the owner can overrule any of them)

- The AI never edits a kept program in place; it proposes a copy.
- A proposed program is not listed in its show until kept, so the AI never writes `show.json` and nothing that plays can change.
- Going back: the earlier versions of a proposed program are kept in `<root>/ai/history/` until it is kept or discarded.
- `sample` uses the Preview panel's made-up light, not the venue's real ones.
- The owner's rules are a separate file that wins over the bundled rulebook.
- The API key path waits for piece 2 (the panel); piece 1 is Claude Code only.
- The conversation is Claude Code's own in piece 1; PTAH stores none.
